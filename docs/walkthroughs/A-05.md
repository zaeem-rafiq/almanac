# A-05 — eval harness · walkthrough

`python -m almanac eval` scores `extract` + `judge` against the 54 human labels in
`evals/claims.jsonl` and exits non-zero if the pipeline would ship a false correction or miss a
stale one.

```bash
python -m almanac eval
```

Writes `evals/results.md` (the table the README quotes) and `evals/results.json`. Add
`--cache evals/.cache/extraction.json` to score the *same* extraction twice — see "the flake".

## What it reports

| | |
|---|---|
| (a) extraction recall | labelled claims `extract.py` produced a verdict for |
| (b) `claim_type` accuracy | with `structural` as a first-class seventh label, not an unknown |
| (c) per-status precision / recall | all five statuses, each with its denominator |
| (d) hard negatives | illustrative/historical rows wrongly called stale |
| (e) misses | every disagreement with `expected`, `got`, `rule_fired`, and a one-line read |

**The binary gate:** non-zero exit if any hard-negative false positive, or `stale_material`
recall < 0.90.

## How rows are matched, since every number depends on it

A labelled row pairs with a verdict when the verdict's quote **covers ≥ 0.90 of the labelled
quote** in normalised text — whitespace collapsed and curly quotes straightened, which is
`extract._normalise`, extraction's own leniency and nothing looser. Assignment is greedy and
**one-to-one**, so one verdict can never satisfy two labels and inflate recall.

Coverage rather than IoU because the two sides are not trying to be the same string: a label is a
fragment a human chose, an extracted quote is the whole sentence. IoU scores that pair 0.43 and
calls it a miss. The first version of this harness used IoU and reported 8 rows as "not
extracted"; all 8 had been extracted, and all 8 carried the labelled status. ADR-002 D-1 has the
argument and the reason it is not tuning — chiefly that **the gate already passed under the old
criterion**, so the change bought no pass it did not already hold.

The coverage floor is not load-bearing, and the report proves it every run: best coverage is
exactly 1.00 for 51 of 54 rows, then a cliff to 0.67. The sweep prints 0.50 / 0.70 / 0.90 / 1.00
and the band is constant; the sub-band probe exists so a "constant" sweep cannot be confused with
a sweep incapable of moving.

## What the first independent measurement found

Zero status disagreements, on every matched row, in **all five live runs**. `judge.py` rules
correctly on whatever extraction hands it — that is the independent confirmation the
"54/54 agreement" figure from `609af65` was reaching for, and it holds.

It does not reproduce 54/54, because 6 labelled rows never get a verdict of their own. That is an
**extraction granularity** gap, not a judge disagreement, and the two had been reported as one
number. All 6 expect `skip`; every non-`skip` status has precision *and* recall 1.00. **The
pipeline never missed a claim that needed a correction, and never invented one.**

## The flake — and why the floor did not move

The gate failed 2 of 5 live runs. Not because the gate is wrong: `extract.py` resamples every run
(65–82 verdicts on identical input) and sometimes drops line 35, the live i-bond composite rate,
which sits next to the historical-trap sentence about the same entity. Neither `extract.py` nor
`notes.py` pins a `temperature`, so both run at the API default of 1.0.

`temperature=0.0` was the original recommendation and **it is not possible**: `anthropic 1.4.0`
has no `temperature`, `top_p` or `top_k`, and a live call passing it returns HTTP 400,
"`temperature` is deprecated for this model". `output_config.effort="high"` was measured as the
nearest lever and does not help (5/6 vs 4/6, spread unchanged, still drops line 35).

Across 17 live runs, **every** gate failure is the same sentence — line 35, the live i-bond rate
beside line 36's historical sentence about the same entity — so this is one sentence being merged
into its neighbour, not diffuse sampling noise. The revised recommendation is a targeted prompt
change, not applied. See ADR-002 D-5 and its correction.

Lowering the 0.90 floor or moving the gate onto a cached extraction would have turned a red gate
green while changing nothing real. Neither was done. **The gate caught a genuine defect on its
first outing.**

## Proofs

`venv/bin/python scripts/proof_a05.py` → `docs/proofs/A-05.md`. 3 of 4 lines PASS.

The fourth — "ADR-002 lists ≥1 miss reviewed by Zaeem with the fix applied" — **cannot be passed
by the agent**, by design. It reads only entries marked `**Status:** RATIFIED`, and all four
decisions sit at `AWAITING RATIFICATION`. Nothing in `evals/claims.jsonl` was edited;
`tests/test_eval.py::test_run_never_writes_the_labelled_set` hashes the file around a full run to
keep it that way.

**A-05 is not done until D-1..D-5 are ruled on.** The decisions are in
`docs/decisions/ADR-002-eval-loop.md`, each with the quote, expected vs got, `rule_fired`, and a
one-line read of which side I think is wrong.
