## Correction — proof 4 restated and re-proven (2026-09-07)

`docs/proofs/**` is append-only, so this corrects the earlier line rather than editing it.

**The original proof 4 asserted more than it verified.** It claimed the runtime "makes 0 calls to
FMP" but checked only two things: that `env -u FMP_API_KEY python -m almanac facts` exits 0, and
that a **non-recursive** grep for the single literal `financialmodelingprep` matched nothing in
`almanac/*.py`. An exit code is not evidence of network silence, and a one-literal grep is exactly
the weak-negative-assertion flaw the A-01 adversarial review had already flagged for
`test_no_module_but_catalog_calls_the_rate_feeds`. The verdict happened to be right; the evidence
did not establish it.

**Re-proven by hard-blocking the socket layer** (`socket.socket.connect`, `connect_ex`,
`create_connection`, `getaddrinfo` all raise) and then running the command:

```
env -u FMP_API_KEY venv/bin/python /tmp/no_net_proof.py
  -> 15 keys, 0 without a value, exit 0
control: requests.get("https://financialmodelingprep.com/stable/quote?symbol=AAPL")
  -> NetworkAttempted   (the block demonstrably works)
recursive grep for requests.|urllib|httpx|aiohttp|http.client|socket.|financialmodelingprep
across almanac/ and web/  -> no match outside almanac/catalog.py
```

Completing every key with all sockets blocked is a positive demonstration that the resolution path
touched the network zero times, rather than an inference from absence.

```
PROOF A-01 (restated): with FMP_API_KEY unset AND the socket layer blocked, `almanac facts` resolves all 15 keys from facts/catalog.yaml + facts/rates.json and exits 0; a control call proves the block is live; no module outside catalog.py references any network API = PASS
```

Also verified against the fabricated-citation check: `facts/rates.json` contains no FMP reference
of any kind — its `fetched_via` values are `nyfed`, `freddiemac`, `treasury`, `bls`.

## Correction — proof 2 was under-covering (found 2026-09-07 during A-02)

`docs/proofs/**` is append-only, so this corrects the earlier line rather than editing it.

**PROOF A-01 #2 claimed "every manual source_url and every primary_source_url returns HTTP 200
(30 urls checked)". The collection behind it silently dropped history rows.**
`test_every_source_url_returns_200` built its work list as
`urls[f"{entry.key}[history]"] = h.source_url` — one dict slot per *key*, not per history row —
so for any key with more than one sourced history row, only the last row's URL was ever fetched.

At A-01 time every key had exactly one history row, so the bug was invisible and the count was
right. It became real the moment `37d1e87` and A-02 added second rows:

```
sources the catalog carries:  29
sources the old collection reached: 27
silently skipped: k401_employee_deferral[history][1], ibond_composite_rate[history][1]
```

Both skipped rows are the *most recently added* ones — precisely what a url-200 test exists to
catch. This is the same shape as the `effective_to` defect the A-01 review found: a branch that
was only ever exercised in its absent form.

**Fixed** by grouping on the URL and labelling each source with its row index
(`source_urls_to_check()`), which both closes the gap and cuts 27 fetches to 12 distinct URLs.

**The regression test was proven to fail on the old logic** rather than assumed to:
`test_url_check_covers_every_history_row` was run against a re-introduced copy of the collapsed-key
collection and went red —
`collected 12 sources but the catalog carries 29; a source_url is escaping the url-200 check`.
It also asserts that a key with two sourced history rows actually exists, so the test cannot
quietly become vacuous if the catalog is ever reduced to one row per key.

```
PROOF A-01 #2 (restated): every source_url in facts/catalog.yaml — 15 entry-level plus all 14 history rows, 29 sources across 12 distinct URLs — returns HTTP 200 to a scripted client = PASS
```
