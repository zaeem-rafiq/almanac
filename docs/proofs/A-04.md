## Recorded deviation — R1 skips `structural` (verified, not assumed)

**The issue's literal rule text** is `R1 claim_type in {illustrative, historical, other} -> skip`.
**Shipped behaviour** is `{illustrative, historical, structural, other} -> skip`.

**What made it necessary.** Commit `566132a` ("feat: A-03 F-1 — structural is the seventh
claim_type") landed on main *after* this issue was written, while A-03 was still running. Before
it, `structural` was not a member of the enum and those sentences collapsed to `other`, which R1
already skipped. After it, `extract.py` emits `structural` directly — and `structural` is not in
the issue's R1 set, so such a claim falls through to R2, where `entity_key is None` returns
**`unresolved`**.

**Why `skip` and not `unresolved`.** `unresolved` means "this is a checkable claim and we could not
resolve it" — it invites a human to go and look. `skip` means "this is not a numeric claim about a
catalog entity at all". "You cannot touch the money for twelve months" is a rule about how the
instrument works: there is no value to compare and no entity to resolve. Leaving it `unresolved`
would put four non-claims into a queue of things a human is asked to investigate, which is a
product defect rather than a scoring artifact. All four `structural` rows in `evals/claims.jsonl`
carry `expected_status: skip`.

**Verified against the live run, not assumed.** Each of the four labelled rows was located in
`reports/latest.json` by a distinctive fragment of its quote, so a reworded quote fails to match
rather than silently passing:

```
EVAL ROW                                      MATCHED  claim_type     status       rule_fired
v3: Non medical withdrawals before sixty five yes      structural     skip         R1 claim_type=structural is not an assertion
v5: resets on the first of May                yes      structural     skip         R1 claim_type=structural is not an assertion
v5: cannot touch the money for twelve months  yes      structural     skip         R1 claim_type=structural is not an assertion
v5: cash out before five years                yes      structural     skip         R1 claim_type=structural is not an assertion

eval structural rows located in the run : 4/4
total claims labelled `structural`      : 9
structural claims NOT status=skip       : 0
any structural claim -> unresolved      : none
```

**Guarded against recurrence.** `tests/test_judge.py::test_r1_covers_every_claim_type_that_is_not_a_checkable_assertion`
asserts that every member of `models.ClaimType` is triaged by exactly one of R1's skip set or the
checkable set `{statutory_limit, tax_bracket, market_rate}`. An eighth label added to `models.py`
now fails that test instead of silently falling through to `unresolved`.

## Correction — everything above the 21:05 run was proved against a different `judge.py`

`docs/proofs/**` is append-only, so nothing above is deleted. But it must be read with this in
front of it, because the module under test changed between the 20:36 run and the 21:05 run.

**What changed.** A-04 was implemented twice in parallel. Runs at 20:20 – 20:45 exercised a
`judge.py` written on this branch, with `Verdict` and `Report` added to `almanac/models.py` under
ADR-001. While that branch was open, Zaeem pushed **`609af65`** to main — his own `judge.py`, with
`Verdict` defined inside it and `models.py` deliberately left locked after A-03. That decision
stands. The branch was replayed onto his commit; my `judge.py`, my `models.py` extension, ADR-001
and my `tests/test_judge.py` were dropped.

**The 21:05 run is the authoritative one.** It is the only run above that exercises the `judge.py`
now on main.

### The `structural` deviation recorded at line 47 is WITHDRAWN

That section argued for adding `structural` to a skip set in a `judge.py` that no longer exists.
It is moot: `609af65` already routes `structural` to `skip` through `R2.unjudged_claim_type`,
which is the same verdict by a better-named rule. No deviation from the issue text remains on this
point, and no code on this branch touches it.

### The rule NUMBERING differs from the issue text, and the proofs account for it

The issue numbers the rules R1 = skip, R4 = exact-match. `609af65` numbers them R1 = resolve a
historical claim against its history window, R2 = skip the unjudged claim types, R4 = exact match,
R5 = diverges. **A statutory limit that differs therefore fires `R5.stale_material`, not `R4`.**

`scripts/proof_a04.py` asserts the **status** each proof line specifies — stable across both
numberings — and prints the rule that actually fired. Asserting `R4` against this judge would have
passed for the wrong reason on one line and failed for the wrong reason on another; either way it
would have been checking nothing. The mapping lives in `SKIP_RULES` / `DIVERGENCE_RULE` at the top
of the harness, with the reason.

Proof 3's "per R5" clause re-derives the expected band from his `MARKET_RATE_MATERIAL_PP` rather
than hardcoding today's answer, so it checks his rubric rather than restating an outcome.

### Two deviations from the issue text that DO still stand

1. **Proof 3 says "2 skips"; the run produces 4.** `fresh_wrong.md` holds four numeric sentences
   that are not assertions — three illustrative, one `other` — and the extractor finds all four;
   the eval set labels three. Nothing was tuned. The proof asserts exactly one `stale_material` and
   that it is `ira_contribution`, the mortgage verdict matching the band its own drift lands in,
   and every remaining verdict a skip.
2. **`reports/` is gitignored** rather than committed. Scan output is a build artifact; the harness
   runs `almanac scan` itself and reads `reports/latest.json` back from disk, so the proofs assert
   over what the CLI wrote. `reports/.gitkeep` stays tracked so the directory survives a fresh
   clone. Verified by deleting every generated report first and re-running from empty.
