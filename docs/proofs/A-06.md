## Scope — this issue does NOT close on this run

Three of the four proofs are in scope. The fourth is deferred by Zaeem's decision:

    PROOF A-06: scan --source youtube status counts == scan --source corpus status counts
      = DEFERRED

**Reason.** HAC-42 lists "A-04 PASS" as a precondition, but that is only true of this one
proof — it needs a `scan --source {corpus,youtube}` command. When A-06 began, A-04 had not
started (it was blocked on A-03, running in a parallel worktree). A-04 has since landed
`extract` and `judge`, but **no `scan` subcommand exists yet**, so the comparison still cannot
be run. Blocking all of A-06 behind it would have cost more than deferring the single proof
that actually depends on it.

**What was done instead of nothing.** `almanac/youtube.py` returns `Source` records carrying
`source_id` / `text` / `locators` — the same shape the corpus reader yields — so A-04's `scan`
consumes `--source youtube` and `--source corpus` behind one interface. The deferred proof
becomes a comparison A-04 can run without reworking this module.
`tests/test_youtube.py::test_corpus_and_youtube_sources_are_the_same_shape` holds that
promise now, offline, so the interface cannot drift before A-04 arrives.

**A-06 is therefore NOT marked closed.**

**Update — the reason changed.** A-04 has since landed `scan`, and its `--source youtube` seam
is wired to `read_youtube_sources()`. The corpus half ran:
`{correct: 1, skip: 54, stale_immaterial: 1, stale_material: 6, unresolved: 3}` across 5 videos.
The YouTube half then hit **HTTP 403 `quotaExceeded`** — seeding the channel cost the entire
10,000-unit daily allocation (`videos.insert` is 1600 units, not the 1 first recorded; see
ADR-000). So the proof is no longer blocked on missing code, only on the quota reset. It is a
single command once the quota rolls over:

```bash
venv/bin/python -m almanac scan --source youtube --out reports/youtube --no-notes
```

then compare `counts` against `reports/corpus/latest.json`.

Worth noting that A-04's session caught a defect in this seam before it could matter:
`iter_sources` defaults to `origin="corpus"`, so calling it bare would have made this very proof
pass **by comparing the corpus against itself**. `scan` now prefers `read_youtube_sources()`,
which cannot be pointed anywhere else.

## In-scope proofs

| # | Proof | Where it is checked |
|---|---|---|
| 1 | `list_channel_videos` returns 5 ids matching corpus `meta.json` | `prove_ids_match` |

### Proof 1 counts both sides on purpose

A-01 shipped a url-200 check that silently skipped 2 of 29 rows and still printed PASS,
because it keyed a dict per-entry instead of per-row. Proof 1 asserts, separately: the channel
holds exactly 5 uploads, the corpus holds exactly 5 folders, all 5 folders matched an upload
by title, no upload is left unclaimed, no two folders map to one id, and every `meta.json`
`video_id` is a real 11-character YouTube id rather than a placeholder. Four uploads out of
five cannot look like five.

### Proof 2 is run against a control that must go red first

A negative assertion proves nothing until it can be shown to fail. `prove_caption_fidelity`
first scores a deliberately corrupted caption and returns FAIL — regardless of how clean the
real diff looks — unless that control breaches the 2% threshold.

Building that control found a real bug in the comparator. The first version tokenised the raw
SRT, so cue indices and timestamps ("00:00:02,800" → several word-like fragments) counted as
words. Being identical on both sides, they padded the denominator with guaranteed matches: a
caption with 3% of its real words rewritten scored **1.4%** and slid under the threshold. The
comparator now parses the SRT and compares caption body only. Measured on
`v1-401k-limits-explained` (534 words):

| input | word diff | required |
|---|---|---|
| corrupted control (1 word in every 3rd cue) | 3.37% | > 2% — red ✓ |
| casing changed on every cue | 0.00% | < 2% ✓ |
| cues re-segmented (pairs merged) | 0.00% | < 2% ✓ |
| one word changed out of 534 | 0.19% | — sensitivity reference |

Cosmetic round-trip artefacts are tolerated; content drift is not.

### Proof 4 is counted, not estimated

`QuotaLedger` records every call the scan makes. Call counts are **observed**; unit costs are
**documented** (YouTube's published quota table — the discovery document carries no cost
metadata). The two are reported separately so neither is mistaken for the other.

    channels.list        1 x   1 =    1
    playlistItems.list   1 x   1 =    1
    videos.list          1 x   1 =    1
    captions.list        5 x  50 =  250
    captions.download    5 x 200 = 1000
                                 ------
                         TOTAL     1253   < 1500 ✓

247 units of headroom, one spare caption download. Against the 10,000/day project quota a full
scan is ~13%.

**Correction, 2026-09-07.** This table first read 1008 units, because the ledger priced every
`.list` call at 1. **`captions.list` costs 50**, not 1 — the captions resource is expensive
across the board, and pricing a family of endpoints by their verb rather than by name
understated the scan by 245 units. Caught by checking the published cost table instead of
carrying the assumption forward; two independent reads of
`developers.google.com/youtube/v3/determine_quota_cost` agree. The ledger now holds an explicit
per-endpoint table, an unpriced endpoint costs 1 rather than 0, and
`test_captions_list_is_not_priced_like_a_cheap_list` pins the values. The proof still passes,
but it now passes against the real number.

`captions.download` is absent from the published table; 200 is the figure HAC-42 states and is
carried on the issue's authority rather than as an independent observation.

Note on the G-2 evidence: the first run recorded `tfmt="srt"` accepted on a track later found to
be ASR. The finding stands — `srt` is accepted — and it has since been re-confirmed against the
**uploaded** track, so G-2 does not rest on the defective selection.

## Recorded override — video length follows the caption track, not the 20-60s guidance

HAC-42 asks for a "20-60s slideshow". The first build honoured it at 30s and was **wrong**,
and the defect is worth recording because it was invisible from the rendering side.

The corpus caption files run **159-168s** — 53-56 cues at a 3s cadence, ~540 words each. A 30s
video carrying a 162s caption track hides roughly 80% of its own subtitles and cuts off
mid-sentence. A judge clicking through from the review page would see something visibly broken,
which is the opposite of the credibility the corpus was written to establish. It was also a
live risk to proof 2, since a caption track whose cues run past the end of a video is exactly
the kind of thing an ingest pipeline may truncate.

Zaeem's decision: synthesize narration with the macOS built-in `say` and let each video run to
the length of its own caption track. `say` is text-to-speech, not a recording — no human time,
no new dependency. The 20-60s bound existed to keep rendering cheap, not because 30s was
correct. **This is a deliberate override, not drift.**

Alignment is structural rather than hoped for: each cue is spoken as its own segment and laid
in that cue's own slot on the timeline, so speech starts exactly where its subtitle starts.
Synthesising the script in one pass would have drifted within a few sentences.

Two assertions now run on every render and fail the build:

* `abs(video_duration - captions_end) <= 2.0s`. This caught a real bug on its first run: the
  concat demuxer's mandatory trailing image repeat **inherits the preceding `duration`**, which
  silently appended a phantom 51s (212.8s of video against a 161.8s caption track). Output
  length is now pinned with `-t`.
* `mean_volume > -50 dB`. The previous build shipped an `anullsrc` track measuring
  **-91.0 dB** — digital silence that merely existed. A track that exists is not a track that
  plays.

## Defect found by re-running the proofs after the videos went public

Worth recording because of *when* it appeared. The first proof run happened minutes after the
API upload, while the videos were private and YouTube had not yet generated automatic captions.
Only the uploaded track existed, so track selection could not go wrong and every video scored
0.0000%. Hours later, with the videos public and ASR tracks generated, proof 2 went **red**:

    v1 9.5506%   v2 5.5856%   v3 9.8566%   v4 0.0000%   v5 4.9524%

`_english_track` was reading YouTube's **machine transcription** instead of the uploaded
captions. The cause was a case mismatch: the API returns `trackKind` as lowercase `'asr'`, and
the filter tested `trackKind != "ASR"`. Every machine transcript passed a filter written
specifically to exclude it.

Two things make this worse than an ordinary typo, and both are the actual lesson:

* **It failed open.** A negative filter (`!= "ASR"`) admits everything it fails to recognise.
  The replacement is a positive allowlist — `trackKind == "standard"` — which admits nothing it
  does not recognise. Same shape as the A-02 lesson about detectors built from denylists.
* **It was order-dependent, so it looked like flakiness.** Selection took the first survivor,
  so v4 passed purely because YouTube happened to list its uploaded track first. A defect that
  passes on some inputs and not others invites being dismissed as a transient.

And the consequence was precisely the one the function's own docstring warned about: Almanac
would have read ASR text, and a misheard "twenty-three thousand" would have become a fabricated
claim attributed to the creator. A verdict citing words the creator never said is the worst
output this project can produce.

Fixed, re-verified live at **0.0000% on all five**, and pinned by regression tests covering all
four casings of `asr`, both list orderings, the only-ASR case (which must yield nothing rather
than fall back), and deterministic choice among equal candidates.

**The proof did its job.** It was green when the evidence was thin — one track per video — and
went red the moment real conditions arrived. That is the argument for re-running proofs against
the world as it actually ends up, not only as it is at the moment of writing.
